# Feature: binary/media widget file persistence + mediatype-exposed override matching

Branch: `feat/media-persistence-mediatype-matcher` (new, off `main`)
Delivery: single PR, reviewable work units as separate commits
Test runner: `yarn jest`

## Specs

- S1: `WidgetMatcher`/`MatchArgs` (`src/widgets/engine/matchOverride.ts`) must expose `mediatype?: string | null` so a host override can target `dataType: 'binary'` questions by their specific media kind (image/audio/video/file), the same way `appearance` already lets a host target signature/barcode. `resolveWidget` (`src/widgets/engine/registry.ts`) must thread `mediatype` into the override-matching call (today it drops it before calling `pickBest`/matching — confirmed at `registry.ts:72-76`). Match semantics for `mediatype`: read `matchScore`'s existing semantics for `appearance`/`controlType`/`dataType` first and keep `mediatype` consistent with it (same exact-vs-partial matching convention already used there — do not invent a different style for this one field).
- S2: the built-in `ImageWidget`, `VideoWidget`, `AudioWidget`, `FileWidget` (`src/widgets/ImageWidget.tsx`, `VideoWidget.tsx`, `AudioWidget.tsx`, `FileWidget.tsx`) currently call `store.answerQuestion(nodeRef, uri)` with the picker/recorder's raw cache URI (confirmed file:line in prior investigation: `ImageWidget.tsx:232-240`, `VideoWidget.tsx:206-211`, `AudioWidget.tsx:162-176`, `FileWidget.tsx:39-45`). This leaks an internal device path and the cache file can be purged by the OS before submit/reopen. Fix: after obtaining the picker/recorder URI, copy the file into a persistent app-owned directory (follow this repo's existing convention for persistent on-device storage: `expo-file-system/legacy`'s `documentDirectory`, as already used by `packages/xform-native-geo/src/SatelliteTileCache` — see `src/__tests__/integration/satelliteTileCache.test.ts` for the mocking pattern to mirror in new widget tests) under a dedicated subdirectory (e.g. `${FileSystem.documentDirectory}xform-media/`), using a generated collision-safe filename that preserves the original extension (e.g. a uuid + the source extension). Store **only the bare filename** (no path, no `jr://`, no scheme) as the answer value via `store.answerQuestion(nodeRef, filename)` — this is the real ODK/OpenRosa convention for binary question answers (the filename is later matched against a submission's multipart attachment list by the host app); do NOT invent a `jr://`-prefixed answer value, that convention is reserved in this repo for form-authored media references (question label/hint media), not respondent-submitted answers (see `FormAdapter.ts:175-178`'s doc comment on `getLabelMediaUri` for why those are a different concern).
- S3: new public API so a host app can enumerate exactly which locally-persisted files it must attach for a submission, given the form's current binary answers. Add this as an exported helper, not a new `FormAdapter`/`FormSessionStore` method requiring an engine tree walk (simpler, avoids coupling to adapter internals): export `mediaStorageDirectory(): string` and `resolveMediaUri(filename: string): string` from a new module `src/widgets/media/mediaStorage.ts` (or alongside the widgets, wherever fits the existing module layout best — writer's judgment, but it must be reachable from the package's public entry point `src/index.ts`). `resolveMediaUri(filename)` returns the full local URI (`${documentDirectory}xform-media/${filename}`) for a bare filename exactly as stored by S2 — the host calls this once per non-empty binary answer value it reads off its own saved XML, with no adapter/store coupling needed. Export both from the package's existing public surface (check `src/index.ts` for how other widget-adjacent helpers are already exported, and match that pattern).
- S4: regression tests: (a) a test proving the persistence copy actually happens and the stored answer value is a bare filename (not a raw picker URI, not path-qualified) for at least `ImageWidget` and one other of the four widgets (writer's choice, cover the pattern once directly and note in the PR that the other two follow the identical pattern if not independently tested); (b) a test for `resolveMediaUri`/`mediaStorageDirectory`'s exact URI shape; (c) a test proving `mediatype` now actually discriminates override matching (an override registered with `mediatype: 'image/*'` matches an image binary question and not an audio one, using whatever exact-match convention S1 settles on).

## Log

- L1 (verbatim, translated context from the user's Spanish request, paraphrase of the actual exchange preserved): a peer session (tlacuache_app, "Filtro search en productores.csv") reported that binary (photo/video) question answers in the real submitted XML contain the raw on-device picker cache URI (e.g. `file:///data/user/0/com.nuup.tlacuacheapp/cache/ImagePicker/<uuid>.jpeg`) instead of a proper file reference, leaking an internal path and referencing a file the OS may purge before submit/reopen; and that `WidgetMatcher` doesn't expose `mediatype`, blocking the consumer's own forked Image/Video/Audio/File widget overrides (already implemented correctly on their side) from ever being selected over the built-in ones. The repo owner (Erick) confirmed via investigation (file:line evidence) that both claims are accurate, then explicitly authorized implementing both: (1) expose `mediatype` in `WidgetMatcher`, (2) fix the built-in widgets to persist the file and store a correct answer value. When asked whether to design the new host-facing "which files to attach" API unilaterally or coordinate with tlacuache_app first, the user (Erick) chose: design it now.
- Risk: item 3 (contracts others consume) for T2/T3 — this changes what binary questions serialize as their answer value (a wire-format change for anyone currently depending on the old raw-URI value, including the very bug report this fixes) and adds new public exports. T1 is lower risk (additive optional matcher field, no behavior change for existing overrides that don't set `mediatype`) but still touches the shared widget-resolution engine — track it under the same high-risk classification for this feature's verification pass rather than splitting hairs.
- L2 (T2/T3 implementation, dated 2026-10-19): Implemented `src/widgets/media/mediaStorage.ts` exporting `mediaStorageDirectory()`, `resolveMediaUri(filename)`, and an internal `persistMediaFile(sourceUri)` helper used by all four widgets. Follows the `SatelliteTileCache` convention exactly: lazy `require('expo-file-system/legacy')`, `documentDirectory`-based (not `cacheDirectory`), stored under `${documentDirectory}xform-media/`. `persistMediaFile` generates a collision-safe filename (local RFC4122-v4-shaped id, no `uuid` dependency added — none existed in this package) preserving the source extension, copies the file via `FileSystem.copyAsync`, and returns the **bare filename only**. `ImageWidget`, `VideoWidget`, `AudioWidget`, `FileWidget` now call `persistMediaFile` right before `store.answerQuestion` and call `resolveMediaUri` when reading a stored answer back for display/playback (thumbnail/video-player/audio-player all need the real local URI, not the bare filename). `expo-file-system` added to `package.json` as an optional peer dependency, same lazy-require + fallback pattern as the other optional media deps — deviation from a strict "fallback to UnsupportedWidget" reading of that pattern: since expo-file-system only affects *where* a captured file durably lives (not whether capture itself works), `persistMediaFile` degrades to returning the original source URI unchanged when the dep is absent or the copy fails, rather than disabling the whole widget. Exported `mediaStorageDirectory`/`resolveMediaUri` from `src/index.ts` alongside the other widget-adjacent exports. Tests added: `src/__tests__/widgets/mediaStorage.test.ts` (S4b, URI-shape), `src/__tests__/widgets/ImageWidget.persistence.test.tsx` and `src/__tests__/widgets/FileWidget.persistence.test.tsx` (S4a, proving the copy happens and the answer value is a bare filename) — both mock `expo-file-system/legacy` the same way `satelliteTileCache.test.ts` does. VideoWidget/AudioWidget were not independently given dedicated persistence tests; they call the identical `persistMediaFile`/`resolveMediaUri` helpers with the same call shape. Full suite: `yarn jest` → 2090 passed, 1 failed (pre-existing, unrelated `all-widgets-demo.test.tsx` count assertion expecting 83, receiving 85), 118 suites (117 passed/1 failed). Existing `ImageWidget.test.tsx`/`FileWidget.test.tsx`/`VideoWidget.test.tsx`/`AudioWidget.test.tsx` suites were left untouched and still pass unmodified: since they don't mock `expo-file-system/legacy`, the lazy `require` fails in those test files (module resolves to untranspiled TS, which Jest's `transformIgnorePatterns` skips for `expo-file-system`), so `persistMediaFile` falls back to its no-op passthrough and those tests keep observing the original raw-URI values — this was verified, not assumed.
