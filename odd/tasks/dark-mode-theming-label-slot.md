# Feature: surface/text color roles in ThemeOverride + question-label slot + reactive ThemeProvider

Branch: `feat/dark-mode-theming-label-slot` (new, off `main`)
Delivery: single PR, reviewable work units as separate commits
Test runner: `yarn jest`

## Specs

- S1: `ThemeOverride` (`src/theme/theme.ts`) only accepts `color.primary/secondary/tertiary`. `LabelHint`/`BofSurface`/`EofSurface` (`src/form/surfaces.tsx`) and other surface chrome read `t.color.roles.onSurface`/`onSurfaceVariant`/`background`/`onBackground`/`surface`/`surfaceVariant`/`outline`/`outlineVariant` (see `tokens.ts` lines ~29-59 for the full `color.roles` shape) — none of these are overridable today, so a host cannot provide a dark palette; question/group text and surfaces stay fixed to `tokens.ts`'s light values regardless of host theme. Add a new overridable group to `ThemeOverride`, e.g. `color.neutral` (or `color.surface` — writer's call on the best name consistent with the existing `primary/secondary/tertiary` naming, documented either way), accepting the literal surface/text roles directly (`background`, `onBackground`, `surface`, `onSurface`, `surfaceVariant`, `onSurfaceVariant`, `outline`, `outlineVariant` — all optional). Unlike `primary/secondary/tertiary` (a single base color auto-derived into container/on-* via `deriveRoleSet`), these are literal pairs a host supplies directly (a dark palette's `onSurface` isn't *derivable* from its `surface` the way a brand color's container shade is) — do NOT force them through `deriveRoleSet`; merge them directly into `color.roles` in `mergeTheme`, same pattern as the existing `roles[role] = ...` assignment loop but without derivation. Keep full backward compatibility: omitting `color.neutral` must produce byte-identical output to today.
- S2: the per-question label/hint (`<LabelHint label={ev.label} hint={ev.hint} required={nodeState.required} />`, `Form.tsx:787`) has no slot — `FormSlots` (`src/form/slots.ts`) only exposes `renderNavigation`/`renderError`/`renderGroup`/`renderSectionIndicator`/`injectValues`, unlike widgets themselves which are overridable via `WidgetOverride`. Add a new slot, e.g. `renderQuestionLabel`, following the EXACT existing slot convention in `slots.ts` (a `FormQuestionLabelSlotContext` interface carrying whatever's useful to a host — at minimum `label`, `hint`, `required`, and `defaultElement` — plus wiring it through `renderSlot` at the `Form.tsx:787` call site, mirroring how `renderGroup`/`renderSectionIndicator` are already wired elsewhere in `Form.tsx`). Must be fully additive: omitting this slot renders byte-identical output to today (same contract every other slot already upholds — see `slots.ts`'s own doc comment on this).
- S3 (reactive ThemeProvider): `ThemeProvider` (`src/theme/ThemeContext.tsx:34-39`) freezes the theme at mount via `useState(() => mergeTheme(theme))`, documented inline as "D1 — theming is not reactive" / "closed product scope, not a defect". Make it reactive: when the `theme` prop changes on a later render, the provided context value must update so already-mounted consumers (anything using `useTheme()`/`useThemedStyles`) re-render with the new colors, without requiring a remount of the whole form tree. Read the existing doc comment's full reasoning (if there's more context above line 34 explaining WHY it was frozen — check for performance/memoization concerns possibly tied to `useThemedStyles`'s own memoization strategy in `src/theme/ThemeContext.tsx` or wherever it's defined) before changing it; if there was a genuine performance reason (e.g. avoiding re-deriving `deriveRoleSet` or re-creating widget styles on every parent re-render unrelated to theme), preserve that by memoizing `mergeTheme(theme)` keyed on the override's own identity/shallow-equality rather than reintroducing the original performance problem — do not just blindly swap `useState` for always-recomputing-every-render. Document the change's reasoning inline, replacing the outdated "not reactive, not a defect" comment (since it will no longer be true).
- S4: regression tests — (a) a theme-level test proving `color.neutral.onSurface` (or whatever S1 names it) actually ends up in the merged theme's `color.roles.onSurface`, and that omitting it is unchanged from today's default; (b) a `Form` test proving `renderQuestionLabel` receives the right context and its `defaultElement` matches today's un-slotted `LabelHint` output, and that omitting the slot is byte-identical to today; (c) a `ThemeProvider` test proving a theme prop change on an already-mounted provider updates a consuming component's rendered color without unmounting/remounting it.

## Log

- L1 (context, paraphrased from the actual exchange): a peer session (tlacuache_app, "tlacuache-app-29") reported that xform-native's theming has no way to support dark mode for question/group text: `ThemeOverride` only exposes `primary/secondary/tertiary` (not surface/text roles), there's no slot to override the per-question label rendering (unlike widgets, which already go through `WidgetOverride`), and `ThemeProvider` freezes its merged theme at mount by explicit design ("D1 — theming is not reactive, not a defect"), so even fixing the first two wouldn't let an in-app theme toggle take effect without a remount. The repo owner (Erick) verified all three claims directly against the code (`theme.ts`, `ThemeContext.tsx:34-39`, `slots.ts`) before authorizing work, then explicitly chose to implement all three now rather than defer or partially implement.
- Risk: item 3 (contracts others consume) for all three — each is a new/changed public API surface (`ThemeOverride`'s shape, `FormSlots`'s shape, and `ThemeProvider`'s reactivity contract/behavior). T3 additionally carries item 6 risk (a regression here — e.g. reintroducing excess re-renders, or breaking memoization relied on by many widgets — might not be caught by a shallow test) if the original freeze was protecting against a real performance issue; the writer must investigate and document which case applies before deciding the exact memoization shape.
- L2 (implementation, 2026-10-22): T3 investigation — the original freeze (`useState(() => mergeTheme(theme))`) had no supporting perf-measurement comment or benchmark above it; the doc comment only stated "closed product scope, not a defect" (a scope decision, not a documented perf finding). `useThemedStyles` already memoizes styles in a `WeakMap<Theme, WeakMap<Function, unknown>>` keyed on the *merged theme object's own identity*, so the real cost to avoid is re-deriving `mergeTheme`/`deriveRoleSet` and producing a new merged-theme object identity on every render that doesn't actually change the override's content (which would cascade into every `useThemedStyles` consumer re-deriving its styles). Implemented `useMemo(() => mergeTheme(theme), [themeKey])` where `themeKey = theme ? JSON.stringify(theme) : undefined` — a structural/shallow key rather than `theme`'s reference — so a host passing a fresh `ThemeOverride` object literal every render (common pattern) does not thrash `useThemedStyles`'s cache; only an actual content change produces a new merged theme and therefore a new context value. All T1-T4 implemented inline (no delegated writer was used — the perf investigation above was quick enough to do directly without materially growing context).
- Verification: `yarn jest` full suite and `yarn build` both run twice; `yarn build` zero errors both times; `yarn jest` only consistent failure is the pre-existing/documented `all-widgets-demo.test.tsx` 83-vs-85 count mismatch — `AudioWidget`/`FileWidget` media tests flaked on some runs (0 vs 1 call count) but passed in isolation and on other full-suite runs, and reproduce the same way on the pre-feature base commit, confirming they are unrelated ordering-sensitive flakes, not a regression from this feature.
